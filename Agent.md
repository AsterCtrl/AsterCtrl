# AsterCtrl development guide for AI agents

This file is the working contract for future automated changes. It records the
current architecture and the evidence boundary; it is not a product promise.
When code, tests, schemas and prose disagree, inspect the implementation and
tests first, then update the documentation in the same change.

## Source of truth

Use this order when resolving a disagreement:

1. public headers, runtime implementation and tests;
2. versioned JSON Schemas and generated fixtures;
3. `README.md` and the current Sphinx pages;
4. the website repository, which mirrors the current user workflow;
5. development journals, which are historical records and never override current code.

Do not infer support from a header, an interface-query test, a generated file, or
a configured CI job alone. A feature is “supported” only when the relevant
implementation, a reproducible test, and the documented user entrypoint agree.

## Current user model

The supported Linux path is deliberately small:

```text
C++ Module → CMake Package → runtime.yaml → aster run
```

- `runtime.yaml` is the only ordinary Linux runtime configuration.
- The current model has no user-authored `application.yaml`, Application Graph,
  Deployment Graph, Module Port table, or Deployment Lock for local execution.
- Modules register Topic and RPC endpoints in `Initialize()`. Registration is
  sealed before `Start()`; names use instance namespace expansion and one exact
  remap.
- The new Host launcher currently wires Local Channel/RPC. Instance configuration,
  logging identity, namespace/remap and executor binding are isolated per instance.
- `package.yaml` generated by `aster init` is a v1alpha3 Package Manifest. The
  repository-root `package.yaml` and the graph fixtures are legacy v1alpha2 test
  inputs; do not use them as new-project templates.

The cross-node/Zephyr `deployment.yaml` model is a design target, not an executable
v1alpha3 path yet. `aster graph`, `aster resolve` and `aster build` are retained
v1alpha2 regression commands. `aster deploy plan|apply|status` consumes the old
Deployment/Inventory/Bundle format and does not start services or flash firmware.

## Capability boundary

| Area | Current truth |
| --- | --- |
| Linux Runtime | Configuration-driven Package loading, static/dynamic Module composition, lifecycle rollback, typed configuration/parameters, Local Channel/RPC |
| Module ABI | Canonical C tables; thin C++ facade; no STL, exceptions or ambiguous ownership across a Linux plugin boundary |
| bounded Protobuf | `.proto` input, fixed-capacity generated types and codec; production Runtime does not link Google Protobuf |
| CAN/SocketCAN and USB CDC ACM | Retained protocol/Adapter and v1alpha2 generated-node regression coverage; not selectable by the new `aster run` launcher |
| Zephyr | Bounded Runtime and board/adapter work exists, but v1alpha3 static generation and same-source deployment are not complete; compile/qualification is not physical-board evidence |
| CorePlugin | ABI loading/version/interface-query tests only; production lifecycle and backend registration are not complete |
| ROS, AimRT bridge, UDP, IP Transport, recording/replay, distributed monitoring, PIL | Deferred; do not document as available |

Use the labels **Current**, **Legacy regression**, **Planned**, and **Physical
evidence required**. Never mix them in one sentence without naming the boundary.

## Interface and implementation rules

- Keep `ModuleBase`, `CoreRef`, `Initialize`, `Start` and `Shutdown` stable unless
  an intentional alpha break is documented and all examples/tests are migrated.
- Registration belongs in `Initialize()` only. Do not add a second native-C++
  lifecycle path beside the canonical C ABI.
- Keep Runtime, Supervisor, Registry, Platform and Transport implementations out
  of the public Module SDK. Package targets link Interface targets, not Runtime.
- Linux may use dynamic allocation; Zephyr hot paths use bounded storage, no
  exceptions/RTTI, and ISR-to-thread handoff through bounded queues.
- Hardware access belongs to Driver Modules or platform Adapters. Portable
  algorithm Modules must not grow POSIX, Zephyr, HAL or simulation branches.
- Channel/RPC are the public communication concepts. Route IDs, Deployment IDs,
  Hardware Profiles and link budgets belong to the legacy/ future deployment layer,
  not to the ordinary Module tutorial.

## Documentation rules

- Current user instructions must be executable on a clean checkout. Include the
  exact command, required environment and the expected status boundary.
- Say “removed from the current model” for deleted concepts; do not say merely
  “not required”, which implies that the concept still exists as an option.
- Mark old graph, Provider, Capability, Hardware and generated CAN/USB pages as
  v1alpha2 regression material. Put historical design decisions in development
  journals and add a dated “historical snapshot” notice.
- Keep English and Chinese Sphinx pages semantically paired. Update the website
  only from current core documentation; never advertise an unfinished compiler,
  adapter or board smoke as available.
- API pages are generated from public headers through Doxygen XML and Breathe.
  Edit the owning header for API comments. Add an availability note when an API
  exists in the interface but is not implemented on a platform.
- Before finishing a docs change, search for stale names and claims:

  ```sh
  rg -n "asterctl|application\.yaml|Application Graph|Deployment Lock|v1alpha2|CAN|USB|Zephyr" \
    README.md document/sphinx-cn document/sphinx-en
  ```

  Every remaining match must be intentional current guidance, legacy context, or
  a clearly dated historical record.

## Verification checklist

For documentation-only changes:

```sh
git diff --check
uv run --frozen python -m sphinx -W --keep-going -q -b html document/sphinx-en build/document/html
uv run --frozen python -m sphinx -W --keep-going -q -b html document/sphinx-cn build/document/html/zh_CN
```

For a new Linux project, use the uv environment for both configure and build so
that CMake finds the installed `aster_cli` package:

```sh
uv sync --frozen --all-groups
uv run aster init hello-aster
uv run cmake -S hello-aster -B hello-aster/build -G Ninja -DASTERCTRL_SOURCE_DIR="$PWD"
uv run cmake --build hello-aster/build
uv run aster run --runtime hello-aster/build/asterctrl/aster_runtime \
  --config hello-aster/build/runtime.yaml
```

For code changes, run the narrowest relevant tests first, then the matching CMake
preset and CLI tests. CI evidence must be cited by workflow run; a workflow file
that merely contains a job is not a passing result. Physical board claims require
dated board logs and firmware hashes.

## Change and commit discipline

Read surrounding code and call sites before editing. Prefer existing seams and
small changes over new framework layers. Use `apply_patch` for hand edits. Keep
generated output out of source commits unless the repository explicitly tracks it.
Use the project commit style `scope: lowercase summary`, update changelog and
paired docs for public behavior, and keep core and website commits independently
buildable.
